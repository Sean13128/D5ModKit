## The owner's report and what the executable actually does

Sean, 19:30 Addendum (`Reports/D4-PLAYTEST-2-OWNER.md`): class XP for the D4 family rises, but **all stars rise at
once**. The pinned writer says why.

`0x14015F480(unit, target_id, amount, notify)`:

| Address | Instruction | Meaning |
|---|---|---|
| `0x14015F4AA` | `mov r10d, edx` | the target class id is kept in `r10` |
| `0x14015F500` | `call 0x14021EBE0` | family → mastery slot (the extension's wrapper) |
| `0x14015F51C` | `mov ecx, r10d` | **`r10` is the id used from here on; `edx` is never read again** |
| `0x14015F56C` | `call 0x14021EE80` | rank helper: `id % 10` → `ebp`, the last rank the loop may award |
| `0x14015F5D0`..`0x14015F730` | loop | for rank `d` = 0..`ebp`: threshold row via `0x1400744D0`, `new = min(threshold, old + amount)` |
| `0x14015F621`/`0x14015F624` | `cmp ecx,[rdx+4]` / `jne loop tail` | a counter that does **not** complete keeps the award unchanged |
| `0x14015F6E3`/`0x14015F6EE` | `r12 = old - threshold + amount` / `inc ebp` | only a completion replaces the amount with its overflow and extends the rank limit |

So a rank-5 target (what an imported family's units are recruited at) with 7 XP writes `[7,7,7,7,7,7]`. That is the
game's own code and is invisible for native classes because the game only awards their current rank; the extension's
slot mapping is what exposes it. It is not a JobRank clone problem and not six classes sharing one row.

## The fix (independently written, 48 bytes of section growth)

One register write inside the existing mapper wrapper, guarded by the caller's return address:

```
mp_<i>:
    mov rax, qword ptr [rsp + 0x28]   ; the caller's return address (push rbx 8 + frame 0x20)
    mov rdx, 0x14015F505              ; the writer's continuation after its mapper call
    cmp rax, rdx
    jne mp_slot_<i>
    mov r10d, <family base>           ; award order: rank limit 0, the native overflow path carries upward
mp_slot_<i>:
    mov eax, <slot>
```

* the wrapper's answer is unchanged (the slot), so every other consumer is untouched;
* only the writer's own mapper call gets the rewrite — the other 15 mapper sites, and every vanilla id, keep `r10`
  exactly as their caller set it;
* the pure policy is stated as `masteryext.in_family()` / `masteryext.award_target()` (family base for a configured
  family, the id itself otherwise) and matches the documented Oct-16 rule (`target - target % 10`); the assembly is
  generated by this repo's own `_mapper_src`, no Overlord source was copied;
* the wrapper's frame is unchanged (`push rbx` / `sub rsp,0x20` / `add rsp,0x20` / `pop rbx` / `ret`), so its
  `.d5cm` unwind record still describes it and no new routine was added (a tail-jump stub would have collided with
  the emitter's routine separation);
* section `.d5cm` grows from 248 956 to **249 004** bytes; patched exe sha256
  `d616e83c07bc1f23cba231f2a8559d22e50531bc394812b06fde889c91446480`, base `0x14808f000`, 16 mapper sites.

Because the rewrite sits in the writer's own mapper call, **every award path** is covered: the selected-award
wrapper `0x140160E20` (own class or chosen sub-class) and explicit calls such as `0x1401517FC` (quest/reward XP)
that never pass through it.

## Existing saves that already show parallel partial bars

The counters live in the unit record the save stores verbatim; the extension has no save-side code and this fix does
**not** reset, migrate or rewrite anything. Concretely, an imported unit that already has `[60,10,5,0,0,0]` in its
family slot:
* the next award fills star 1 (`[64,14,5,0,0,0]` for 8 XP), star 2 receives the overflow, star 3's stale 5 waits;
* each higher partial becomes the frontier once the stars below it complete, so nothing is lost and nothing is
  double-awarded — the bar just looks staggered for a while;
* completion bonuses already granted stay granted (they are the eight `u16` words at `+0x359C`), and no bonus is
  paid twice because the writer skips it when the old value was already at the threshold.

**A one-time normalisation is possible but is deliberately not implemented or applied.** It would, per configured
family slot, find the first incomplete star `r`, keep `0..r` untouched and zero the partials above `r` (those are
phantom awards from the parallel loop; a *completed* star above `r` cannot occur with the game's increasing
thresholds). It would restore a clean single bar at the cost of discarding whatever pending XP those phantom bars
represent. That is a save mutation and needs Sean's explicit decision; nothing here writes a save. If he wants it,
the safe shape is: back up the save first, edit only slots 47..52 of units whose class/sub-class belongs to a
configured family, keep `+0x359C..` untouched, and verify with the game's own reader (`0x140217230`) before and after.

## Limits

* Native gameplay is not executed: everything is Unicorn over the pinned exe. The "explicit call" and
  "selected wrapper" cases start at the real native call sites and run the real writer, but the frames above them
  are fixtures, not a live battle.
* The selected wrapper's own-class branch for an id above 1310 is **not** widened by this lane (its bound lives in
  `esi`/`edi`, not an immediate): both builds pass target 0 there. The own-class award that matters is the explicit
  `0x1401517FC` call, which is covered. This is pre-existing and belongs to the class lane / REBASE158, and the
  proof now asserts the value so it cannot be mistaken for coverage.
* Windows unwinding is checked structurally (records, codes, sort order, retention) and by the ABI engine's frame
  checks, not by a real `RtlVirtualUnwind` dispatch.
* The sub-class screen's 47-row cap and the six-family limit are unchanged.
* A parallel lane (`REBASE158`, worktree `engine-158`) is porting mastery onto Kit 1.5.8 and fixing the slot
  mapping (review P1). This change touches only `_mapper_src` / `award_target` / `in_family` in
  `d5lib/masteryext.py`, two added tests, and the proofs; there is **no new patch site, no new routine, no change
  to `slots()`, `families_from()`, `MAPPER_CALLS`, the gate, the fetch or the unwind rules**, so it should merge
  cleanly on top of that lane's slot changes. Merge order does not matter for correctness; only the generated
  wrapper bytes change.
