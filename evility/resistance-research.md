# Resistance HP snapshot research (2026-10-30, offline)

No exact D4 Anti Elements row is certified. D5's resistance CALL sees a unit whose max HP can already be under reconstruction, and the HP percentage passed by its caller has lost the precision needed for D4's inclusive threshold. A possible earlier game CALL is identified below; no implementation or proof establishes a safe lifetime for an exact snapshot yet.

## Observations

- The D4 recalc calls `FUN_14010de70(unit, 0xe6, 0)` at 1401b4010 decomp line 1985 and adds the result to three element slots; it writes its new max HP only later (line 2911). Getter `14010de70` replaces zero third argument with unit max at +0xd20, derives a threshold from source evility metadata, and returns zero only if threshold is less than min(current HP at +0xd10, max). If that source threshold byte is 25, the combat comparison is inclusive at its integer-rounded threshold. The display path at 1401a6310 line 1792 uses strict float `< 0.25`. The source evility metadata byte itself remains unverified; the displayed description alone does not prove it.
- Pinned D5 executable entry 0x14021bfb0 is `unit_recalc(unit, mode, battle_record)`. It calculates `HP*100/max` at 0x14021c02a–0x14021c03e, then at 0x14021c058 calls 0x140218c90 (`unit_stats_evil_rebuild_list`) with RCX = unit. This call is before the recalc overwrites or adds equipment to max HP; decomp line 1137 demonstrates later mutation. Current resistance hook wraps 0x14021d964 -> 0x1401f2a10 and receives the caller's precomputed integer percentage in R9, but `hp_below` currently rereads the later unit HP/max fields. Both are insufficient to reproduce an exact prior HP/max comparison: for example 250/1000 and 251/1000 both produce integer 25.
- D5 xrefs list 179 caller functions. A raw pinned `.text` scan for direct E8 relative targets found 264 byte patterns targeting 0x14021bfb0 (candidate call instructions, not independently validated as instructions). Decomp includes calls from battle setup (`script_cmd_battle_setup`), battle actions (`start_basic_attack`), turn updates, menus, and record refresh. Therefore intercepting a small selected set of calls to `unit_recalc` would not cover all contexts.

## Candidate and remaining proof

A CALL wrapper at 0x14021c058 could read the unit's exact current and max HP before forwarding the original call. A matching wrapper at 0x14021d964 could consume them. Neither wrapper's own temporary stack frame persists after it returns, so a process-wide single saved pair is unsafe for nested recalculation, multiple threads, and exceptions. A potential per-invocation solution would store the pair in genuinely unused bytes of the *game's* unit_recalc frame, keyed by that invocation; however no complete stack-liveness analysis or unwind/exception validation has established such bytes. An alternative thread-local linked context needs a lifecycle spanning the entire recalc, including every return and exceptional unwind; wrapping a limited set of callers cannot ensure that. Neither approach has yet been implemented or proved.

To resolve: verify D4 0xe6's actual threshold metadata and integer rounding; establish full D5 frame liveness and ABI/unwind behavior or a complete reentrant context lifecycle; demonstrate exact HP/max at both real CALLs under nested/interleaved invocations, with 250/1000, 251/1000, zero HP, repeated recalculations and changed max; rerun static stack audit, payload verification and regressions. Native behavior remains untested. No game process, save or installed kit was touched.
