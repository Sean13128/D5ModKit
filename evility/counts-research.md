# Filtered counts: Friends source trace (offline, 2026-10-30)

D4 Friends (840 / 0x348) cannot yet be declared equivalent to D5's existing `per: squad` scale. D4 counts other eligible battle units whose Evil Area lists intersect the holder's, with additional team/relationship rules. D5's existing squad helper counts present front roster members in a selected squad; it does not establish intersection, other-unit exclusion, or the same eligibility and relationship rules. No implementation, game install, or live check was performed.

## Source evidence

- `/Volumes/Data/Decomp/d4/functions/1401ba0a0_FUN_1401ba0a0.c`: the outer loop excludes the holder battle record, requires `1400ebe30(record) != 0`, `140108df0(record) != 2`, `1401b1280(unit) == 0`, and `1400eea80(unit) == 0`. On the relevant allied branches it increments `local_288` when `14024b490` returns nonzero; later adds `local_288 * FUN_14010de70(holder,0x348,0)` to the stat accumulator. The normal branch requires identical team bytes. The alternate global-state branch admits some team 0/team 3 cases with additional character-ID restrictions. Preserve the actual branches rather than approximating with a generic relationship name.
- The decompiler omits the third argument of `14024b490`. Disassembly of the installed D4 executable, read offline using Capstone and PE image base, resolves it. At **0x1401bac0e** and **0x1401bad83**, respectively, preceding instructions set `r8 = [r14+0x1f0]` (iterated unit), `rdx = [rsi+0x1f0]` (holder unit), `rcx = 0x140efa678` (manager), then call `0x14024b490`. Both branches pass the same roles. The increment follows at 0x1401bac17 / 0x1401bad8c. This is an observed game CALL, not a hook or proof for a D5 wrapper.
- `14024b490` loops over both units' lists and returns true on any common entry. `1400e92e0(unit)` reads signed count byte at `unit+0x189e`; `1400e9280(unit,i)` reads signed entry byte at `unit+0x183e+i`. Source text identifies the relevant concept as Evil Area; the machine-level fact is list intersection, not simply a shared first slot.
- Eligibility helper details: `1400ebe30` reads battle-record signed byte +0x294; `140108df0` returns 2 on invalid/dead path and otherwise a Boolean; `1401b1280` excludes unit class +0x1808 in 0x33–0x34 or family +0x1806 == 0x1e1; `1400eea80` excludes three unit IDs at +0x1132. Exact cross-game identities and corresponding D5 eligibility are not yet established.

## Prior art checked

- Cryswar's Overlord `overlord/10_evility_runtime.c:785–808,820` supplies general map-unit counts and `count_same_squad_units`; it does not implement this source list-intersection and relationship filter. The Kit port `OLEFFECTS-REPORT.md` identifies `per: squad` as D5's native `0x1401d3990` helper. Credit Cryswar if reusing that design.
- Sorrow `RESEARCH-INDEX.md` and `ida-export-20261014/disgaea5_names.json`: `unit_stats_squads_has_squad` 0x1401d44f0 and `unit_stats_squads_squad_members` 0x1401d3990 are navigation evidence for D5 membership and present front roster counts.
- D5 decomp `1401d44f0_unit_stats_squads_has_squad.c` checks a unit squad list at +0x30a0 with count +0x30a1; `1401d3990_unit_stats_squads_squad_members.c` searches 20 stored squad UIDs and checks presence in front roster. Its author annotation notes that count byte aliases an entry; no assertion of valid multiple memberships is made here. This is related prior art, not evidence of Evil Area equivalence or of matching D4 battlefield filters.
- D4 decomp and the two actual executable CALLs above establish source mechanics. No matching D5 hook site has been selected, no ABI proof or payload verification has been run, and no native gameplay equivalence has been demonstrated.

Next: establish a D4 Evil Area to D5 representation and battle-unit eligibility/relationship mapping, including multiple memberships and other-unit exclusion. Only then select an unowned game CALL, implement, prove normal and ABI paths, and validate content ownership and native behavior. Until then, keep Friends omitted rather than silently substituting squad count.

## Miasma 114 (0x72): source versus D5 aura

**Verdict: the current resistance aura is not an exact Miasma port.** D4 applies each eligible hostile provider's value; the current `near_has` aura only tests whether at least one provider exists. Multiple providers therefore differ. Spatial footprints and an additional D4 recipient gate also differ or remain unproved.

- In D4 `1401ba0a0`, the other-record loop first applies the eligibility checks described above. At the shared adjacency branch, executable CALL **0x1401bb189** passes `rcx = recipient battle record`, `rdx = candidate battle record`, `r8d = 1` to `1400ed660`. Its decomp resolves coordinates including an alternate coordinate field and delegates to `1400ed6f0` / `1400ed5c0`, testing both records' footprints. Their BSim annotations identify D5 counterparts `0x140153f30` / `0x140154200` as likely matches, but those annotations do not prove a usable call ABI or effect equivalence.
- After that spatial gate, `14022d830(candidate_team,recipient_team)` indexes the 4x4 D4 relationship table. For each accepted provider, source checks `1400ec4d0(recipient) == 0`, reads its evility 0x72 and subtracts it separately from all three element accumulators, eventually stored at unit +0x118c/0x118e/0x1190. `1400ec4d0` returns true when `14025cc50() == 6` and recipient byte +0x115e is nonzero. The meanings and corresponding D5 condition are unproved. The Ghidra local-register reconstruction for the first subtraction should be checked against machine code before asserting exact accumulator sequencing.
- D5 `d5lib/native/d5evil.inc.asm:333` implements `evil_near` by scanning active, uncarried battle records, excluding subject, using an inlined D5 hostile-team table, and computing Manhattan distance from each record's single `evil_cell`. `docs/EVILITIES.md` explicitly says footprint is not considered. Thus a large provider or recipient can have adjacent occupied cells while its origin cells are more than one panel apart; source path can accept this while current aura misses it. Relationship table and special recipient gate parity remain unverified.
- The `near_has` aura condition is existential, not a provider count, so adding a -20 row once cannot reproduce two qualifying D4 providers each contributing -20. Other conditions and per-row resistance arithmetic must also be checked; these observations alone block an exact label.

**Prior art:** Cryswar's `10_evility_runtime.c` `EFFECT_ELEMENT_RESISTANCE_PERCENT` calls `count_aura_holders` and supports once versus per-holder stacking, operation and clamp. This is a useful blueprint, but its native collector's spatial and eligibility behavior must still be compared to the D4 gates. Sorrow's D5 naming and both decomp footprint helper matches are navigation evidence, not proof. The D5 resistance worktree changes are offline only; no test, install, or gameplay acceptance was performed for this trace.

### Candidate D5 collector and remaining barriers

- Existing resistance CALL wrapper site is **0x14021d964 -> 0x1401f2a10** in `unit_recalc`; it is already owned by the current resistance carrier, so improve that wrapper/evaluator rather than claiming a second patch at the same site. It receives `rcx=unit`, `rdx=battle context`, `r8=18-dword modifier accumulator`, `r9=HP percent`, fifth stack arg SP percent. Current `wrap_resistance` saves unit/accumulator and calls original, then `evil_apply`; to use a collector it must preserve and pass the battle context through safely, with the normal and `--abi` proofs and static stack audit required by LANE-RULES. This analysis does not certify the wrapper.
- Sorrow `neigh` **0x1401f4020** takes `(out, evility_id, reference_actor, relation, range, flags)` and returns count. Its bit 4 forces fallback **0x1401f4190**, bypassing the precomputed-neighbor path. That path walks 256 battle records, checks active unit and class index, rejects certain D5 character/type IDs, uses bit 1 to exclude carried units, and for range != -1 uses recipient `menus_env_cost_map` coordinates and candidate world-position cells with **0x140153f30** footprint comparison. `relation=2` asks `model_team_is_hostile(candidate_team, recipient_team)`. The latter ordering agrees structurally with D4's `14022d830(candidate,recipient)`, but the relationship table values and exceptional D4 class gates require explicit comparison. The recipient coordinate-selection behavior versus D4's `1400ed660` alternative coordinate fields also remains unproved.
- A candidate is `neigh(out, -1, reference_actor, 2, 1, 5)` (hostile, radius one, carried-excluded, force footprint path), then inspect each returned candidate for the actual active custom evility and sum each provider's actual configured magnitude, preserving D4 eligibility and recipient mode gate. The output buffer must fit the collector's maximum 256 four-byte slots and the stack frame must maintain Windows x64 alignment and shadow/stack arguments. This is a design candidate only. Passing the custom evility ID directly to `neigh` uses `0x1402068b0`, which tests the D5 sorted +0x2f30 status list; compatibility with EVCAP and all learned/innate sources must be established, and it may not reconstruct source-specific per-holder magnitude. Passing -1 and filtering through a proven active-EVCAP lookup avoids assuming native-ID support, but still needs tests for its real semantics.
- The forced-fallback collector has extra D5 type/ID exclusions (`events_env_kind_of(...) == 2`, ID groups 0x33/0x34/0x30 and 5000..5009); D4 excludes its own separate type and ID classes. We cannot establish those classify the same entities across games from the present evidence. Likewise the D4 suppression gate is global `DAT_1418e94c0 == 6` AND recipient byte +0x115e != 0; no D5 mapping has been established. These are concrete fidelity barriers. Exact Miasma should remain omitted until the gates and actual source arithmetic/order are verified; a footprint-aware per-holder D5 approximation could be explicitly labeled if requested, but is not source-exact.
- Overlord `10_evility_runtime.c:1300` implements the counted aura using `count_aura_holders` and configurable per-holder stacking. Its `hook_collect_units` forwards to the original and does not itself add support for custom status IDs. Sorrow names above and the D4/D5 decomp were consulted; no additional game CALL or patch has been claimed or tested.
