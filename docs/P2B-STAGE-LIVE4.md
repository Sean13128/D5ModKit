Do not interpret generated records or a packed pool as proof of native menu capacity, persistence, or uninstall safety.

Follow `LANE-RULES.md`, including PLAY and the window-hiding rule. No installation or launch is part of this offline task.

## LIVE4 acceptance checklist

Use one live operator, a migrated **copy** of a suitable save, and an isolated test output log. If `live-harness/PLAY` exists, stop; never minimize the game. Start through `d5link.Game.launch_steam()` so `hide_game.sh` runs, or start the hiding script explicitly for any other launch. Keep Save2 untouched. Record candidate build and mapping hashes, save-copy identity, pre-test backup and screenshots. Failure at any point stops the run and triggers the rollback below.

- [ ] With the game fully restarted after installation, reach the hub on the migrated copy. Check the migrated pilot's name, level, class/row, subclass, counters and unlocks against the pre-migration receipt. Check Valvatorez separately as a unique pilot.
- [ ] Use `python Subprojects/Engine-Extensions/live-harness/hub.py classes --json` to capture the actual Recruiter entries, IDs and unlocked rank counts. The grid has a 47-entry window: if an intended family is absent, establish actual navigation/paging before claiming it is unavailable or passed. Verify all six rank rows and selectability for every family when their unlock prerequisites are met; do not assume all six are unlocked on this save. Record each rank name and `ranks_unlocked`.
- [ ] For each of the 16 family IDs above, use `hub.py create <actual-recruiter-family-id> --rank 0` and then `hub.py verify <actual-created-class-id>`; record output and compare the returned unit's class ID with the expected installed mapping. The selection rank is zero-based. If the grid uses a physical ID rather than the listed logical family, resolve it from the verified build manifest; do not guess. Create a vanilla control with the same flow. Verify roster uniqueness, class IDs and six-rank selection as unlocked. `hub.py` uses the remote pipe and **does not save**; it creates units only for the current session.
- [ ] For each new unit, exercise the real award path in battle with a controlled award and capture the six counters/stars before and after. Confirm only the earliest incomplete star advances per award, later stars remain unchanged, and awards attach to the intended family; repeat across rank transitions. Do the same for the vanilla control and compare with its baseline. Record amounts, counters, thresholds and screenshots; creation and class-list output alone do not prove awards.
- [ ] Separately exercise persistence on a copied save using an authorized, validated save workflow: the harness's `remote=1` refuses game saves, so do not claim reload persistence from its in-memory units. Close the game and use the approved process to save the test copy, restart/reload it, and compare the exact class, rank and mastery counters with the pre-reload receipt. If no safe workflow is available, mark persistence **blocked**, not passed. Include a safe full-pool/overflow test only on a disposable copy; verify no corruption or eviction and report the observed behavior.
- [ ] Check the Recruiter cost and personality screens for the created units, plus the known fidelity/animation limitations in the package manifests. Report native results independently from offline proof and Sean's later playtest.

## Rollback

Close the game. Preserve the test copy and logs; never overwrite the original save with it. Use the currently installed Kit's canonical restore mechanism and its existing backup state, restore the previously recorded profile and mappings without manual reassignment, and verify the pre-stage archive/exe hashes and absence of interrupted backup intents. Re-enable the harness pipe after a vanilla restore if a subsequent test needs it. Restart before checking the restored profile. Do not load a save containing custom-class references under an unpatched/removed profile until a separate removal-safety test has established that it is safe; restoring files alone does not prove save compatibility. If restoration fails, stop and retain backups for recovery.
